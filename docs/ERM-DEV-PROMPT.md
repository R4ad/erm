## بخش ۱ — راه‌اندازی روی سرور

### وضعیت فعلی سرور (از خروجی ترمینال)

- **کارهای انجام‌شده:**
  - تغییرات کامیت‌نشده‌ی سرور در کامیت `8d6a640a` («snapshot: serever state before redesign») روی شاخه‌ی `figma-frontend` ذخیره شده است. این کامیت هنوز push نشده و فقط روی سرور است.
  - شاخه‌ی `feature/questionnaire-risk-identification` از روی همین کامیت ساخته شده است.
  - Claude Code نصب است.
- **پیام `X11 forwarding request failed on channel 0`** خطا نیست؛ هشدار SSH است و `git fetch` کار کرده است (بی‌خروجی یعنی تغییر تازه‌ای روی GitHub نبوده). برای حذف این هشدار، در `/root/.ssh/config` زیر `Host github-erm-dev` این خط را اضافه کنید:
  ```
  ForwardX11 no
  ```
- **فیگما از سرور در دسترس نیست:** فیگما محل این سرور را مسدود کرده است (HTTP 451). این محدودیت از طرف خود فیگماست، پس هیچ راه اتصالی به فیگما (MCP رسمی، توکن شخصی یا Framelink) روی این سرور کار نمی‌کند. سرور MCP فیگما را حذف کنید:
  ```bash
  claude mcp remove figma -s user
  ```
  به‌جایش، مرجع طراحی روی لپ‌تاپ از فیگما خروجی گرفته شده و به‌صورت فایل در `docs/design/` به سرور می‌رسد.

### آیا فیگما روی لینوکس نصب می‌شود؟

نسخه‌ی دسکتاپ رسمی برای لینوکس وجود ندارد؛ فیگما روی لینوکس در مرورگر اجرا می‌شود. روی این سرور اصلاً به فیگما نیاز نیست: Claude طراحی را از فایل‌های `docs/design/` می‌خواند. ویرایش طراحی همچنان روی لپ‌تاپ انجام می‌شود.

### ۱. گرفتن این فایل و مرجع طراحی از GitHub

این فایل و پوشه‌ی `docs/design/` از لپ‌تاپ روی شاخه‌ی `design-handoff` در `R4ad/erm` push می‌شوند. روی سرور:

```bash
cd /opt/erm-dev
git checkout feature/questionnaire-risk-identification
git fetch origin design-handoff
git checkout origin/design-handoff -- docs/ERM-DEV-PROMPT.md docs/design
git commit -m "docs: design handoff for questionnaire risk identification"
ls docs/design/frames      # باید ۱۳ فایل PNG ببینید
```

اختیاری ولی توصیه‌شده: اگر کلید GitHub سرور اجازه‌ی نوشتن دارد، شاخه را push کنید تا نسخه‌ای از کار فعلی سرور (از جمله کامیت snapshot) روی GitHub هم بماند:

```bash
git push -u origin feature/questionnaire-risk-identification
```

### ۲. پشتیبان دیتابیس توسعه

محیط توسعه همان `docker-compose.dev.yml` است (README، بخش «توسعه روی سرور»). مطمئن شوید `.env` شامل `COMPOSE_FILE=docker-compose.dev.yml` است، بعد:

```bash
cd /opt/erm-dev
docker compose ps
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > ~/erm-dev-db-$(date +%F).sql
ls -lh ~/erm-dev-db-*.sql
```

کد در گیت ذخیره شده است. برای اطمینان بیشتر یک کپی کامل هم بگیرید:

```bash
tar -czf ~/erm-dev-code-$(date +%F).tar.gz -C /opt erm-dev
```

نسخه‌ی تستی سامانه (`docker-compose.yml` در پوشه‌ای دیگر) به این کار ربطی ندارد و دست نمی‌خورد.

### ۳. اجرا با کاربر غیر root (توصیه‌شده)

خط فرمان شما `root@…` است. Claude Code را بهتر است با کاربر معمولی اجرا کنید. با root، هر دستوری که تأیید کنید به کل سرور دسترسی دارد.

```bash
# با root
adduser --disabled-password --gecos "" erm
usermod -aG docker erm
chown -R erm:erm /opt/erm-dev
install -d -m 700 -o erm -g erm /home/erm/.ssh
cp /root/.ssh/config /home/erm/.ssh/config
cp /root/.ssh/<کلید-github-erm-dev> /home/erm/.ssh/      # نام کلید را از IdentityFile در config بردارید
sed -i 's#/root/#/home/erm/#g' /home/erm/.ssh/config
chown -R erm:erm /home/erm/.ssh && chmod 600 /home/erm/.ssh/*
su - erm
cd /opt/erm-dev && git fetch      # باید بدون خطا کار کند
```

بعد Claude Code را برای همین کاربر نصب کنید و وارد شوید (گام ۴).

- عضویت در گروه docker هم عملاً دسترسی سطح root است. فایده‌ی اصلی این کار، مالکیت درست فایل‌ها و جلوگیری از اجرای ناخواسته‌ی دستورها با root است.
- اگر الان فرصت این کار نیست، با root ادامه دهید، ولی هر دستور را قبل از تأیید بخوانید و از `--dangerously-skip-permissions` استفاده نکنید.

### ۴. اجرای Claude Code

```bash
claude update                 # یا نصب: curl -fsSL https://claude.ai/install.sh | bash
tmux new -s erm               # تا با قطع SSH کار متوقف نشود
cd /opt/erm-dev && claude
```

با Shift+Tab به **Plan mode** بروید و بنویسید:

```
فایل docs/ERM-DEV-PROMPT.md را کامل بخوان و «بخش ۲ — پرامپت سشن» را اجرا کن. طبق گام ۱ اول فقط بررسی و برنامه را آماده کن و منتظر تأیید من بمان.
```

- Claude فایل `CLAUDE.md` پروژه را خودش می‌خواند.
- بعد از تأیید برنامه، از Plan mode خارج شوید تا Claude پیاده‌سازی را مرحله‌به‌مرحله انجام دهد.
- جدا شدن از tmux با `Ctrl+b` و بعد `d`؛ برگشتن با `tmux attach -t erm`؛ ادامه‌ی آخرین سشن با `claude --continue`.
- اگر سشن طولانی و سنگین شد، سشن تازه بزنید و بگویید «از docs/implementation-plan.md ادامه بده».

### ۵. دیدن نتیجه

رابط فقط روی `127.0.0.1:5173` سرور باز است. از دستگاهی که با آن به سرور SSH می‌زنید:

```bash
ssh -L 5173:127.0.0.1:5173 <user>@<server>
# بعد در مرورگر: http://localhost:5173/app/
```

VS Code با Remote-SSH این تونل را خودش می‌سازد.

**LLM:** به‌طور پیش‌فرض `LLM_PROVIDER=mock` است، یعنی کل جریان بدون مدل واقعی هم کار می‌کند. برای وصل کردن مدل داخلی، در `.env`:

```
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=http://<host>:<port>/v1
LLM_MODEL=<model-name>
LLM_API_KEY=<key-if-needed>
```

### اگر طراحی در فیگما تغییر کرد

روی لپ‌تاپ دوباره از فریم‌ها خروجی بگیرید و روی شاخه‌ی `design-handoff` push کنید. روی سرور همان دستور `git checkout origin/design-handoff -- docs/design` را بعد از `git fetch` بزنید و به Claude بگویید چه فریمی عوض شده است.

### نقش و هدف

تو مهندس ارشد فول‌استک این مخزن هستی: سامانه‌ی مدیریت ریسک سازمانی (ERM) داتین، با Django و DRF در بک‌اند و React در `frontend/`. ماژول «شناسایی ریسک از پاسخنامه» را **کامل، هم بک‌اند و هم فرانت‌اند**، دقیقاً مطابق طراحی در `docs/design/` بساز. بخشی از این ماژول در کد موجود است؛ کار تو ارتقای آن به طراحی و منطق جدید است، بدون خراب کردن بقیه‌ی سامانه و بدون از دست رفتن داده. رابط فارسی، راست‌به‌چپ و مینیمال است.

### منابع حقیقت و ترتیب اولویت

1. دستورهای من در همین سشن.
2. **طراحی در `docs/design/`** برای ظاهر، متن‌ها، حالت‌ها و جریان صفحه‌ها. این پوشه خروجی فایل فیگماست و مرجع است: اگر کد موجود با آن فرق دارد، کد را تغییر بده، حتی منطق را.

### اسکوپ

**داخل اسکوپ:**

- آیتم «پاسخ به پرسشنامه‌ها» در سایدبار (میز کار).
- ویزارد ۸ گامی پاسخ به پرسشنامه، ذخیره‌ی پیش‌نویس، ارسال و فهرست پاسخنامه‌های اخیر با وضعیت.

### آنچه از مخزن می‌دانیم (پیش از استفاده بررسی کن)

**پشته:**
- Django + DRF، پایتون ۳٫۱۴ و pipenv، PostgreSQL 17.
- اپ‌ها در `apps/`؛ API در `apps/api/` (`urls.py`، یک ماژول برای هر بخش)؛ رابط React زیر `/app/`.

**فرانت:**
- `frontend/`: React 19، TypeScript، Vite، Tailwind 4، Radix، TanStack Query، react-hook-form، zod و lucide-react.
- ساختار: `src/features/*`؛ مسیرها در `src/app/routes.tsx`؛ منو در `src/components/layout/nav.tsx`.
- رنگ‌ها فقط در `src/styles/index.css` تعریف می‌شوند (`DESIGN.md`).

**تست و اجرا:**
- pytest، vitest، Playwright و axe (`frontend/e2e`).
- محیط توسعه: `docker-compose.dev.yml` با نام پروژه‌ی `erm-dev` و سرویس‌های `db`، `web` (runserver) و `frontend` (Vite روی `127.0.0.1:5173`).
- دستورها داخل کانتینرها اجرا می‌شوند (README، «توسعه روی سرور»):
  - `docker compose exec web pytest`
  - `docker compose exec frontend npm test`
  - `docker compose exec frontend npm run lint`
- اگر با کاربر غیر root کار می‌کنی، فایل‌هایی را که داخل کانتینر ساخته می‌شوند (مثل مایگریشن) با `docker compose exec -u "$(id -u):$(id -g)" web …` بساز تا مالکشان root نشود.

**زیرساخت‌های قابل استفاده:**
- **کار پس‌زمینه:** Celery نیست. الگوی پروژه یک management command حلقه‌ای است (`monitor_risks --watch` در سرویس `monitoring`).
- **روز کاری:** `apps/workcalendar/workdays.py` (`add_working_days`، `working_days_between`). پنجشنبه، جمعه و تعطیلات رسمی روز کاری نیستند و روز شروع شمرده نمی‌شود.
- **تاریخچه:** simple-history و اپ `audit`، به‌اضافه‌ی خط زمانی ریسک. هیچ سابقه‌ای حذف یا ویرایش نمی‌شود.
- **کد ریسک:** `RK-{سال شمسی}-{شماره}` از قبل وجود دارد و کد داده‌شده دوباره داده نمی‌شود.

**مدل‌های موجود مرتبط:**
- `apps/questionnaires/models.py`:
  - `Response`: وضعیت‌های `draft` پیش‌نویس، `submitted` ارسال‌شده، `returned` برگشت‌خورده و `reviewed` بررسی‌شده؛ فیلدهای ثابت (`functions`، `mission`، `commitments`، `disruptive_event`، `conditions`، `consequence`)؛ و `structured_data`.
  - ساختار پاسخ: `ServiceRecord` ← `RiskInstance` (`trigger`، `event`، `scope`) ← `RiskPath` ← `PathConsequence`، به‌اضافه‌ی `PathControl` و `InitialEvidence`.
  - `PendingRisk`: وضعیت‌های pending / converted / dismissed، با `dismiss_reason`، `duplicate_of`، `decided_by` و پیوند به `Risk`.
- `apps/risks/models.py`:
  - `Risk.Status` با ۹ مقدار: questions، registered، submitted، assessment، rejected، treatment_plan، treatment، review، closed.
  - `Risk.Channel` (شامل questionnaire)، `RiskCategory` (از مایگریشن 0012 اختیاری) و `IdentificationDraft` (فرم شناسایی دستی).
- فرانت موجود:
  - `features/questionnaires`: ResponseWizard، StructuredResponse، ReviewPages، PendingConvertPage، RiskQuestionsPage و status.tsx.
  - `features/identification`.

**کار نیمه‌تمامی که فقط روی این سرور بود:** کامیت `8d6a640a` («snapshot: serever state before redesign») تلاش قبلی برای همین صفحه‌هاست. شامل:
- `apps/api/questionnaire_answers.py`
- `QuestionnaireAnswersPage`، `IdentificationWizard`، `RecentEntries`، `modes.ts`، `steps.tsx`، `use-wizard-page.ts`
- `apps/risks/migrations/0013_identification_status.py`

### قاعده‌ی اصلی و مدل داده‌ی ماژول

**قاعده‌ی اصلی: به ازای هر پیامد متمایز دقیقاً یک ریسک ساخته می‌شود.** گروه‌بندی را کد انجام می‌دهد، نه LLM: مسیرهایی که رویداد مشترک دارند در یک گروه‌اند. مثال: ۳ مسیر که مسیر ۳ رویداد ۱ را دوباره استفاده می‌کند، یعنی ۲ پیامد و در نتیجه ۲ ریسک، و ریسک ۱ دو مسیر دارد.

- هر مسیر دقیقاً به یک رویداد وصل است: رویداد جدید یا رویداد یکی از مسیرهای قبلی.
- هر رویداد یکتا دقیقاً یک پیامد دارد. رویداد دوباره‌استفاده‌شده پیامدش را با خودش می‌آورد.
- رویدادی که هنوز مسیری از آن استفاده می‌کند حذف نمی‌شود. رویداد مشترک فقط از مسیر مبدأش ویرایش می‌شود.

**فیلدهای ریسک پیشنهادی و ریسک تأییدشده:**

- عنوان (ساخته‌ی AI و قابل ویرایش)
- عامل آغازگر (شروع رویداد)
- مسیر تحقق (یک یا چند، با پیوند به مسیرهای پاسخنامه)
- رویداد هدف
- پیامد (متن، نوع، دامنه)
- دسته‌ی ریسک
- مالک ریسک
- روش شناسایی (خودکار و فقط‌خواندنی)
- پیوند به پاسخنامه و پیامد منبع
- اطمینان و دلیلش، کمبودها
- `ai_original` (برای «بازگرداندن پیشنهاد AI» و برچسب «ویرایش‌شده»)
- ریسک‌های مشابه، تأییدکننده و زمان تأیید

### ماشین‌های وضعیت (مقدارها بعد از تأیید نگاشت)

**پاسخنامه:**

### شناسایی هوشمند (LLM)

جزئیات کامل در **بخش ۳** است. پرامپت و اسکیما را عیناً در کد بگذار، مثلاً `prompts/risk_identification/v3/system.md` و `schema.json`.

1. **ناهمگام، با الگوی پروژه:**
   - مدل `AiRun` (وضعیت، مرحله، نسخه‌ی پرامپت، مدل، هش ورودی، خروجی خام، خطا و کد پیگیری).
   - یک management command حلقه‌ای (مثلاً `run_ai_identification --watch`) به‌عنوان سرویس در `docker-compose.dev.yml` و در `docker-compose.yml` (پروفایل prod)، مثل `monitoring`.
   - رابط مرحله‌ها را با polling از TanStack Query نشان می‌دهد. کاربر می‌تواند صفحه را ترک کند و در پایان اعلان می‌گیرد.
2. **گروه‌بندی با کد:** کد گروه‌بندی بر اساس پیامد را انجام می‌دهد. اگر هیچ گروه کاملی نیست، LLM فراخوانی نمی‌شود و حالت «ریسکی ساخته نشد» نمایش داده می‌شود. `allowed_categories` از `RiskCategory`های فعال می‌آید.
3. **adapter مستقل از سرویس‌دهنده:**
   - `mock`: پیش‌فرض توسعه و تست. ریسک‌ها را مستقیم از متن گروه‌ها می‌سازد.
   - `openai_compatible`: برای سرورهای داخلی مثل vLLM یا Ollama.
   - تنظیمات با django-environ: `LLM_PROVIDER`، `LLM_BASE_URL`، `LLM_MODEL`، `LLM_API_KEY`، `LLM_TIMEOUT_MS=60000`.
   - اگر سرور از خروجی ساختاریافته با JSON Schema پشتیبانی می‌کند، از آن استفاده کن.
   - اضافه کردن کتابخانه‌ی پایتون (مثلاً httpx) تأیید من را می‌خواهد. کتابخانه‌ی استاندارد هم کافی است.
4. **اعتبارسنجی** طبق بخش ۳. در صورت شکست، یک بار تلاش دوباره با فهرست خطاها؛ بعد حالت خطا با کد پیگیری. پیش‌نویس ناقص ذخیره نمی‌شود.
5. **ریسک مشابه** در بک‌اند پیدا می‌شود، نه با LLM: `django.contrib.postgres` با `TrigramExtension` در مایگریشن و `TrigramSimilarity` روی عنوان، رویداد هدف و پیامد. آستانه قابل تنظیم و حداکثر ۳ مورد.
6. **حریم خصوصی و لاگ:** نام پاسخ‌دهنده و داده‌ی شخصی به LLM ارسال نشود. نسخه‌ی پرامپت، مدل، هش ورودی، خروجی خام، زمان و نتیجه‌ی اعتبارسنجی لاگ شوند.
